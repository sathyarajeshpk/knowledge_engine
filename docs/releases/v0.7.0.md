# Release Notes — v0.7.0

**Milestone:** M6 — Weekly automation
**Date:** 2026-08-01
**Schema version:** 1 (unchanged)
**Status:** The engine runs itself.

---

## Executive summary

Every milestone until now was run by a person. M6 is the first one that runs
without anybody there.

That sounds like a small change and is not. An engine a human executes reports
to a human who is reading the output at that moment. An engine on a cron reports
to nobody, holds credentials, and has permission to write to the repository —
and its failures are silent by default. Most of this release is about that gap.

Two things arrived together, because they had to:

**The engine became observable.** A weekly digest, written every week including
the empty ones, so that "nothing happened" and "the engine stopped working" stop
producing the same evidence. Notifications through two independent channels,
neither of which can fail a harvest.

**The engine became reviewable as a security surface.** From M6 onward every
milestone ships a Security & Vulnerability Review. This one covers ten areas
and reports six findings, none high severity — and it found two real defects
while being written.

| | v0.6.0 (M5) | v0.7.0 (M6) |
|---|---|---|
| How it runs | By hand | **Sunday 06:00 UTC** |
| Weekly digest | none | **`digests/YYYY-Www.md`, always written** |
| Notification channels | none | **GitHub Issue + SMTP** |
| Concurrent-mint protection | none | **File lock + workflow concurrency group** |
| Security review | none | **10 areas, 6 findings** |
| Tests | 366 | **465** |
| Runtime dependencies | 2 | **2** |

## What you can now do

Nothing, on Sundays. That is the feature.

```bash
# What the scheduler runs
ke harvest --notify

# What you get, in the repository
domain-packs/microsoft-fabric/digests/2026-W31.md

# And, if configured, in your inbox and as a GitHub Issue
```

Notifications are configured by repository secrets and are entirely optional:

| Secret | Channel |
|---|---|
| *(none — uses the job's `GITHUB_TOKEN`)* | GitHub Issue |
| `KE_SMTP_HOST`, `KE_SMTP_USER`, `KE_SMTP_PASSWORD`, `KE_SMTP_TO` | Email |

An unset secret means a skipped channel, not a failed run. The engine works with
no secrets at all.

## The digest

One file per ISO week. Three rules, each preventing a specific way a scheduled
system goes quietly wrong (ADR-0037):

**It is written even when nothing was found.** Otherwise "no updates this week"
and "the harvest never ran" leave identical evidence — which is to say, none.
The empty digest says so in words.

**The review backlog is in it, above the headline counts.** The current live
figure is 72 items. A queue mentioned in a footnote is a queue nobody works.

**Problems come before successes.** Dead sources, then errors, then warnings,
then the numbers. A digest that leads with "12 new items" and buries an
unreachable source below the fold has told you the wrong thing first.

A real one, from this branch:

```
# microsoft-fabric — 2026-W31

## Summary
| Discovered | 344 |
| **New knowledge objects** | **0** |
| Updated | 0 |
| Unchanged | 302 |

## 📋 72 item(s) awaiting review
queued: 26 · revision: 1 · unclassified: 45

## New this week
_Nothing new. Every source was read successfully and reported no updates the
engine had not already stored._
```

That is a genuinely quiet week reported as one — 344 items seen across the
sources, every one of them already known.

There is a fourth, smaller thing the digest buys: a commit lands every week, so
GitHub's 60-day auto-disable rule for inactive scheduled workflows can never
trigger. An engine that publishes only when it finds something would switch
itself off during a quiet spell — exactly when nobody would notice.

## Three defects found and fixed

The maintainer's standing note across M2–M5 — *a successful pipeline execution
does not guarantee correct output* — held for a sixth milestone. This time two of
the three were found by the security suite and one by fixing a test.

### A source-supplied title could forge structure in the stored article

A title is rendered as the `# ` heading of `feature.md`, and nothing forced it
onto one line. A title containing a newline followed by `# ` produced a **second
heading**. A source able to forge structure in a stored document can make an
object appear to be a different feature than its `metadata.yaml` says it is.

`ke validate` compares the pair and would eventually have caught the
disagreement — but detection after the fact is the wrong layer for input the
engine controls entirely. Titles are now single-line by type invariant, enforced
on `RawItem` and `KnowledgeObject` so it holds for every adapter including ones
not yet written.

No churn: a title already on one line is unchanged, and all 222 stored objects
still validate with no new findings.

### A pack with no classification rules silently defaulted every object

`classify_objects` returned early when a pack had no rules. It looked like a
harmless optimisation. What it did was store every object in such a pack with
`category: None`, a default `tier`, and `needs_review: False` — so nothing
reached the review queue, and the run reported success.

That is the silent guess ADR-0010 forbids, wearing the costume of a clean
harvest. It is not hypothetical: it is the state **every new domain pack starts
in**, and M8 exists to add one. Microsoft Fabric was unaffected only because it
has rules.

Found by tightening a digest test I had written with a conditional assertion —
`if total:` — which would have let it pass while asserting nothing. The
generalisable lesson: *a conditional assertion is a test that has been given
permission to prove nothing.*

### A command finding no packs exited 0 having done nothing

`ke harvest --repo-root <wrong path>` printed nothing and succeeded. A mistyped
path, or a checkout that did not include `domain-packs/`, would have made the
weekly workflow report a green run every week while harvesting nothing at all.

Invisible by construction, and precisely the failure the 60-day auto-disable
rule punishes. Finding no packs is now an error that names the directory it
searched.

## Security

Full review: [`docs/reviews/M6_SECURITY_REVIEW.md`](../reviews/M6_SECURITY_REVIEW.md).

Ten areas, organised around one question: **what can a hostile source do?**
Everything the engine ingests comes from the public internet, and none of it is
trustworthy just because Microsoft published it.

**Six findings, none high severity.**

| | Severity | Status |
|---|---|---|
| S-1 No dependency pinning or hash verification | Medium | TD-6, M7 |
| S-2 Actions pinned by tag, not SHA | Medium | TD-8, M7 |
| S-3 Redaction is best-effort | Low | Accepted, documented in ADR-0038 |
| S-4 No CVE scanning | Low | TD-7, M7 |
| S-5 Stale-lock reclamation trade-off | Info | Accepted |
| S-6 Notification content is not authenticated | Info | Accepted for M6 |

Controls worth naming:

* **Credentials have one blast radius.** No module outside `ke/notify/` reads
  `os.environ` at all — asserted, and mutation-tested.
* **Redaction is pattern-based, not only value-based.** Scrubbing known values
  protects secrets the engine holds; patterns also catch the ones it never held,
  which are the ones nobody registered and therefore the ones that leak.
* **`git add domain-packs/` is a containment boundary.** A harvest that could
  commit outside the pack could modify the engine that runs it next week.
* **No shell execution and one network egress point** in the entire engine, both
  enforced by scanning and both demonstrated to fire.

## Testing

**465 tests, up from 366.** Every one offline and deterministic.

The push step — the only shell in M6, running unattended, failing by
half-publishing a harvest — is tested by **extracting it from the workflow YAML
and running it** against real local Git repositories. Read from the YAML rather
than copied, because a copy drifts and a test of a copy proves nothing about
what runs on Sunday.

Verified by mutation rather than by passing:

| Mutation to the workflow | Caught by |
|---|---|
| `git add -A` instead of `git add domain-packs/` | containment test |
| `exit 0` on final push failure | rejected-push and rollback tests |
| All rebasing removed | concurrent hand-edit test |

That last case is the one the rebase exists for. Learning state is user-owned
and hand-edited; a weekly push that could clobber it would make the entire
field-ownership model worthless.

## Upgrading

Nothing to do. No schema change, no migration, no stored object touched.

To enable the schedule, the workflow needs to exist on the default branch — it
takes effect once this is merged. To enable email, set the four `KE_SMTP_*`
repository secrets; to skip email, set nothing.

## Known limitations

* **Dependencies resolve at workflow time.** No lockfile, no hash pinning. Two
  dependencies, both very widely used, but a compromised release would run
  inside the harvest. TD-6.
* **Actions pinned to `@v4` / `@v5`,** which trusts the tag not to move. TD-8.
* **Redaction cannot be complete.** A novel credential format could reach a
  GitHub Issue. Defence in depth, stated as such rather than implied.
* **The stale-lock window is one hour.** A harvest running longer than that
  could be joined by a second one. The workflow's 20-minute timeout makes this
  impossible on the scheduled path.
* **The 35 objects with polluted revision history** from M3 remain, still
  surfaced as `REV002` warnings. They truthfully record what the engine did at
  the time, and rewriting history to make a warning go away would be the worse
  trade.
* **The engine has not yet run on a real Sunday.** Everything here is verified
  locally and by `workflow_dispatch` reasoning; the first genuinely unattended
  run happens after merge.
