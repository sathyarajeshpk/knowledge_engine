# Release Notes — v0.2.0

**Milestone:** M1 — Discovery
**Date:** 2026-08-01
**Schema version:** 1 (unchanged)
**Status:** Second release

---

## Executive summary

M0 built the container. M1 fills it — carefully.

The engine can now **look at the internet and report what it found**. It fetches
every configured source, parses each into normalised items, works out what each
item *is*, decides how much that identity can be trusted, notices when a source
breaks, and falls back to a second source when one fails.

**It still writes nothing.** No knowledge objects, no Feature IDs, no state
files. That was not an omission — it was the point. Feature IDs are permanent and
never reused, so discovery is the last stage where a mistake is free. Every
significant decision in this release was made *because* nothing had been written
yet, and two of them would have been unaffordable a month later.

The headline is not the adapters. It is that **the architecture changed twice, on
measurement, before anything permanent existed**.

## What was built

### Discovery adapters

Three, behind one interface — `discover() -> list[RawItem]` — so that nothing
downstream ever learns where knowledge came from.

- **`html_table`** — the primary. Microsoft Learn "What's New" pages. A streaming
  `HTMLParser` state machine that walks `<h2>` sections and the table rows
  beneath them.
- **`markdown_table`** — the secondary. The same content from the
  `MicrosoftDocs` repository: same authority, different infrastructure,
  different failure modes.
- **`feed`** — RSS and Atom, via `feedparser`.

### The safety machinery

| Capability | What it prevents |
|---|---|
| **Injected clock** ([ADR-0021](../adr/0021-injected-clock.md)) | Timestamps that cannot be reproduced. Enforced by a test that greps the package for `datetime.now(` |
| **Identity hierarchy** ([ADR-0023](../adr/0023-stable-item-identity.md)) | A reworded headline minting a second permanent Feature ID |
| **Identity confidence** ([ADR-0028](../adr/0028-identity-confidence.md)) | Minting from an identity we do not actually trust |
| **Collision detection** ([ADR-0027](../adr/0027-announcement-feature-knowledge-object.md)) | Distinct features silently merged into one object |
| **Source health + fallback** ([ADR-0019](../adr/0019-source-health-and-fallback.md)) | A dead source looking like a quiet week |
| **Lifecycle** ([ADR-0029](../adr/0029-knowledge-lifecycle.md)) | "Not finished processing" being indistinguishable from "out of date" |
| **Acquisition boundary** ([ADR-0030](../adr/0030-acquisition-subsystem.md)) | The pipeline becoming un-reusable one convenient import at a time |

## Major architectural decisions

### Announcement, Feature, Knowledge Object are three things ([ADR-0027](../adr/0027-announcement-feature-knowledge-object.md))

The engine had assumed **one announcement URL identifies one update**. That is
true for feeds, where each entry has its own permalink. It is false for curated
update tables — and Microsoft's are curated update tables.

An **Announcement** is a published artifact that *reports* features. A
**Feature** is the unit of knowledge and owns the permanent ID. A **Knowledge
Object** is the stored record. An announcement has a one-to-many relationship
with features.

> An announcement URL is a **citation**, not an identity. It says where knowledge
> was reported, not what the knowledge is.

### Identity confidence gates minting ([ADR-0028](../adr/0028-identity-confidence.md))

`identity_basis` says what an identity rests on. It cannot say whether that is
*good enough to mint from* — a canonical URL identifying one feature and a
canonical URL identifying a blog post covering eleven are both `canonical-url`.

```
HIGH    durable anchor AND the announcement reports exactly one feature → mints
MEDIUM  shared announcement, or a weak anchor                           → queues
LOW     nothing durable to rest on                        → never mints, ever
```

The distinction that makes it sound:

> **Identity is permanent and run-independent.
> Confidence is a per-run assessment of whether minting is safe yet.**

Confidence may use run-scoped evidence — *how many features share this
announcement* — precisely because it never enters the ID. Identity may not,
because an identity that changes when a row stops appearing is not permanent.
A test pins this: grading an item alongside others must not change its identity
key.

Named levels, not a score. A numeric score invites a tunable threshold, and a
tunable threshold is a dial someone eventually turns to make a backlog go away.

### Acquisition is a subsystem with an enforced boundary ([ADR-0030](../adr/0030-acquisition-subsystem.md))

Discovery, identity, confidence and review turned out to be one thing. Eight more
Domain Packs are planned and knowledge will eventually arrive from APIs, PDFs and
videos, so each should need **a new adapter and nothing else**.

The boundary is checked by import scanning, not documented and hoped for. The
forbidden list names modules that do not exist yet (`store`, `classify`,
`indexer`…) — which is when the rule is cheapest to enforce, before the code that
would break it is written.

### Provenance is a chain, not a bag ([ADR-0026](../adr/0026-discovery-chain-provenance.md))

```
Source → Representation → Adapter → Version → Method → Identity basis
       → Date precision → Date confidence → Knowledge Object
```

Stored in that order, so an object reads as a narrative. `source_representation`
is separate from `adapter_type` because the same knowledge reaches us as rendered
HTML *and* as source Markdown, and "which did this come from?" is a question the
adapter name stops answering the moment a source grows a second one.

## Discoveries

Everything here was found by **measuring production**, not by reasoning about
fixtures. That distinction is the most valuable thing this milestone produced.

### No purpose-built update feed is reachable

Every `blog.fabric.microsoft.com` and `powerbi.microsoft.com` feed returns **403
from a GitHub Actions runner**, including with a browser User-Agent. Learn itself
is fine: no CDN challenge, no header dependency, permitted by `robots.txt`.

### One announcement, eleven features

The largest cluster on the live Fabric page is a monthly summary post cited by
**18 rows covering 11 independent features**. **75% of all discovered items** cite
an announcement blog post rather than a documentation page.

### A date scraped out of a sentence

```
| Data Factory gateway manual update (Preview) | The Gateway
  December 2025 release adds a manual update option. |
```

The adapter searched the whole row for a date, found "December 2025" **inside
prose**, and labelled it `EXACT`. One row in 361 — rare, silent, and destined to
become a permanent Feature ID minted from a month mentioned in a sentence.

### The measurements that decided the design

| Identity scheme | Features | Agreement | Merged groups |
|---|---|---|---|
| URL only (today) | 214 | **98%** | 16 |
| URL + title | 242 | **35%** | 0 |
| URL + title + category | **315** | 34% | 0 |
| Title only | 241 | 35% | 0 |

Adding the title fixes merging completely and **collapses stability from 98% to
35%**. Adding the category produces 315 identities from 315 rows — de-duplication
stops working entirely.

## Assumptions that were disproven

This is the section worth re-reading before M2.

### 1. "RSS will be the primary source"

**Assumed:** Microsoft publishes update feeds; the HTML page is a fallback.
**Reality:** every candidate feed 403s from a runner. The one high-signal source
is a web page.
**Consequence:** the milestone inverted. HTML became primary and carries the load
RSS was designed for.
**Caught by:** validating every endpoint on a runner *before* writing adapters.

### 2. "One URL identifies one update"

**Assumed** silently by ADR-0023 — never written down, which is why it survived
review.
**Reality:** false for curated tables. 16 identity groups merge genuinely
different features; ~28 features would have been silently absent.
**Consequence:** the three-level model, and gating on confidence.
**Caught by:** a probe written to check something else.

### 3. "The Markdown source is a weaker copy of the HTML page"

**Assumed:** the secondary is a degraded version of the primary.
**Reality:** it has *better* identity quality (97% durable vs 93%) — it is only
secondary because its links are relative and must be reconstructed.
**Consequence:** the fallback is genuinely equivalent, not a consolation prize.

### 4. "A fallback that responds is a fallback that works"

**Assumed:** if the secondary returns items, failover is safe.
**Reality:** what matters is whether the two **agree on identity**. Fabric agrees
96%; a scheme scoring 35% would mint duplicates for two-thirds of the pack on the
first failover.
**Consequence:** `tools/fallback_probe.py`, and the composite-identity change
being deferred rather than adopted.

### 5. "Marking a source `disabled` disables it"

**Assumed:** `status: disabled` works everywhere.
**Reality:** `_discover_chain` only checked `is_pollable` for *top-level* sources.
On a fallback it was decorative — the retired link would still be polled on the
next failure.
**Consequence:** fixed, and pinned by a test asserting the URL is never fetched.
**Caught by:** trying to use the feature.

### 6. "Category is a good identity discriminator"

**Assumed** (reasonably) when it was proposed.
**Reality:** 28% of features appear under 2–3 sections, and sections encode
lifecycle state — so a feature reaching GA would move sections and mint a second
permanent ID, contradicting ADR-0009.
**Consequence:** rejected, with the measurement recorded so it is not proposed
again on intuition.

### 7. "Power BI's weak fallback should be disabled"

**Assumed:** 73% identity agreement makes the Power BI secondary dangerous.
**Reality:** once minting was gated, both representations yield **the same 14
high-confidence items** — and those are exactly the 14 whose identities agree.
Failover mints the same objects, not duplicates.
**Consequence:** the source-level switch was the wrong instrument; a per-item gate
is strictly better. Re-enabled.

## Lessons carried forward

**Measure the source; do not reason about it.** Three defects were found by
running against production and none by reading the code. The fixtures were
written from *measured* structure and still missed the prose-date bug. This is now
written into the playbook.

**Write a probe to answer one question; expect it to answer a different one.**
`fallback_probe.py` was built to check whether the secondary worked. It found the
identity-merging defect instead — the most consequential finding of the milestone.

**A milestone that writes nothing is worth having.** Every architectural change
here was affordable *because* no Feature ID existed. The same findings three
weeks into M2 would have cost a pack full of permanent, un-correctable IDs.
Consider keeping this property for as long as possible in future milestones.

**Enforce architectural rules with tests, not documentation.** The clock rule, the
acquisition boundary and the adapter contract are all checked by code that fails
CI. Each guard was verified to fail when a violation is introduced — *a test that
cannot trip is decoration*.

**Two questions means two fields.** `date_precision`/`date_confidence`,
`SourceStatus`/`HealthState`, `lifecycle`/`status`,
`identity_basis`/`identity_confidence`. Every one of these started as a proposal
to overload a single field, and every separation has since earned itself.

**Name the state you created.** Gating minting produced knowledge that is
discovered but not stored. Without `Lifecycle` that state would have been inferred
from side effects — and inferred states are the ones that go wrong quietly.

**Pin known limitations with tests.** `test_title_identity_does_not_survive_a_verb_change`
asserts a *weakness*, so nobody later mistakes it for a bug and "fixes" it by
growing a noise list that would cause worse collisions.

## Known limitations

- **The merging defect is contained, not solved.** 15 collisions covering ~28
  features need human triage. The fix that closes it outright is deferred on
  evidence, not on effort.
- **A review queue nobody drains is a slower kind of data loss** than the merging
  it replaced. `ke review` is promoted into M2 for exactly this reason.
- **`low` confidence currently matches nothing.** No present source produces
  titleless rows. It is a floor for sources not yet onboarded, not a level doing
  work today.
- **Power BI carries a heavier review burden** — 44% of primary items queue
  against Fabric's 21% — and has **zero** publication dates, so its Feature IDs
  take the discovery month permanently.
- **Source health is computed but not persisted** (M6), so parser-break detection
  is inert in production today.
- **The acquisition boundary is one-sided** until M2 gives it something to hold
  back.
- **`identity.TITLE_NOISE` is Microsoft-flavoured vocabulary living in code**,
  violating the subsystem's own "no vendor logic outside an adapter" rule.
  Recorded with its trigger rather than left to be discovered.
- **Lifecycle `superseded` and `status: replaced` read similarly** and mean
  different things. The softest part of the design; flagged for M5.
- **`models.py` is past 1,400 lines.** Splitting it is cheap now and expensive
  later.

## Breaking changes

None for stored knowledge — nothing is stored yet, and `SCHEMA_VERSION` is
unchanged at 1.

For anyone importing the package directly, module paths moved:

```python
from ke.identity import compute_identity      # before
from ke.acquisition import compute_identity   # after
```

`ItemIdentity` and `IdentityBasis` now live in `ke.models`, because core types
must not depend on the subsystem that computes them.

## What's coming in M2 — Identity, dedupe, storage

The milestone where knowledge becomes **permanent**:

- `ids.py` — date-based minting with per-month counters
- `dedupe.py` — URL hash, content fingerprint, near-duplicate detection
- `store.py` — the object directory, atomic writes
- **`ke review`** — working the queue, promoted from M9
- `ke harvest`, and an idempotency test proving a second run changes nothing

Two obligations M2 inherits, both easy to get wrong:

1. **A queued item must keep its `first_discovered_date`.** Otherwise review
   latency silently shifts a permanent Feature ID's month.
2. **The queue must be drainable.** The gate is only an improvement if the
   knowledge it holds back eventually gets through.

## Why M1 matters

M0 made it possible to store knowledge safely. M1 made it possible to *acquire*
knowledge safely — and, more importantly, established the working method the rest
of the project will run on: **validate against reality before committing to a
design, and let measurement overrule the plan.**

The engine still writes nothing. It is now ready to.
