# Release Notes — v0.4.0

**Milestone:** M3 — The update path
**Date:** 2026-08-01
**Schema version:** 1 (unchanged)
**Status:** The engine can now revisit what it wrote.

---

## Executive summary

M2 taught the engine to write. **M3 makes it safe to run unattended.**

The difference is one promise, made in M0 and untested until now: *the weekly
automated job must never destroy the notes, learning progress and relationships
you added by hand.* Until this release the engine only ever created objects, so
that promise had never actually been put at risk.

It has now been put at risk deliberately, against production data, and it held.

| | v0.3.0 (M2) | v0.4.0 (M3) |
|---|---|---|
| Can create objects | ✅ | ✅ |
| Can **update** objects | ❌ | ✅ |
| Tests | 287 | **319** |
| Regression tests | 0 (implicit) | **11 explicit** |
| No-op harvest changes | — | **exactly 1 file** |

## The proof

A live object was hand-edited with learning state, notes, relationships, a locked
`difficulty` and a hand-written artifact. Its stored title and content hash were
corrupted to force a real update, then `ke harvest` ran against the live sources:

## Regression tests came first

As instructed, before any new functionality. One per bug that reached a running
system — and each records **why the existing tests could not see it**, which is
what stops a future refactor deleting it as a duplicate:

| Bug | The blind spot |
|---|---|
| Run ID recomputed per call | `FrozenClock` is stable by construction — the test clock did not have the bug |
| 222 orphaned `feature.md` files | Every test wrote through the happy path; nothing modelled the two writes as interruptible |
| All 222 objects failed validation | Storage and validation were each tested, never one after the other. The bug lived in the seam |
| Review keys could not be pasted back | `approve()` was tested with the full key the test itself held |
| YAML anchors in metadata | Nothing asserted on rendered text; every check round-tripped through the parser |

**Every one was verified to fail against the old behaviour before being
committed.** A test that has never failed is a claim, not a guard.

## What changed

**`revisions.py`** decides what a sighting actually changed, and appends a
revision only when it is material. Reflowed whitespace is not news;
`identity_confidence` drifting on its own is not news either — it is a per-run
assessment that can shift when an unrelated item stops sharing an announcement.

**Updates use an allow-list** ([ADR-0033](../adr/0033-update-scope.md)).
`UPDATABLE_FIELDS` is a strict subset of the engine-owned set: `id`, `slug`,
`discovered_date`, `provenance` and `revisions` are engine-owned but **not
re-derivable from a later sighting**, so they are frozen after minting. Two
import-time assertions make a contradiction impossible to ship, and a new field
is frozen by default rather than updatable by default.

**`update_object` compares before writing**, so a run that changes nothing leaves
the bytes — and the mtime — alone.

## Assumptions that were disproven

### 1. "If two sources report one feature, dedupe handles it"

**Reality:** dedupe stopped the second sighting from *minting*, but not from
*updating*. Both matched the stored object, both ran the update, and the object
flipped between the two sources' renderings — **twice per harvest, forever**.

**Measured:** 70 "updates" on a run that changed nothing, and a permanently
dirty git diff. A weekly diff that is always dirty is the same as no diff at all.

**Fix:** one sighting per identity, from an already-deterministic order.

### 2. "An end-to-end test covers the code it names"

`update_object`'s byte-comparison is unreachable from the pipeline —
`detect_changes` short-circuits first. **Deleting the comparison entirely left
every test green.**

**Lesson worth generalising:** a test that still passes when you delete the code
it claims to cover is not testing that code. Both tests were rewritten to say
which guard they actually exercise.

### 3. "Engine-owned means safe to overwrite"

Four engine-owned fields must never be refreshed from a later sighting, because a
later sighting knows nothing about them. Ownership answers *who may write*;
it does not answer *whether a value can be re-derived*.

## Known limitations

- **No retirement path.** A feature that vanishes from its source keeps its
  object, with nothing marking it. Follows "never delete existing knowledge", but
  the pack will accumulate silently-retired items (TD-10).
- **`provenance` is frozen at first discovery**, so an object found via HTML and
  later seen only in Markdown still reports HTML provenance (TD-11).
- **`harvest_pack` now does seven things** and should be decomposed before M4
  (TD-1, escalated to High).
- **The 26-item review queue is still undrained**, with no bulk triage (TD-8).
- Full list in [`M3_ARCHITECTURE_REVIEW.md`](../reviews/M3_ARCHITECTURE_REVIEW.md) §7.

## Breaking changes

None. `SCHEMA_VERSION` stays **1**. No stored object changed shape; 35 existing
objects were reconciled to their canonical first-sighting metadata on the first
run of the new update path.

## What's coming in M4 — Classification

Tier, learning priority, category, difficulty and workload, from rules in
`pack.yml` rather than in code. M4 is the first milestone to write the
**engine-proposed** class — the one where `overrides` has to hold — and the first
where a rule tweak could rewrite 222 objects at once if classification is not
deterministic.
