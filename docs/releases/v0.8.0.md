## Executive summary

Six milestones built a machine for getting knowledge **in**. This is the first
one about getting it **out**, and it is where the project's central claim stops
being architectural and becomes something you can run.

That claim was: *separate the knowledge from the intelligence*. Until now it was
a bet — a repository of well-structured Markdown that no AI had ever touched.
`ke generate` is where the bet pays off, and it pays off by **not** building the
integration everyone expects.

There is no API client. No key, no endpoint, no bill, no rate limit. `ke
generate` prints a self-contained document; you paste it into whichever model you
like; you paste the answer back. The entire AI integration is a human with a
clipboard, and every one of those properties is deliberate (ADR-0040).

| | v0.7.0 (M6) | v0.8.0 (M7) |
|---|---|---|
| Find something | read the indexes | **`ke search`, 12 filters** |
| Use it with a model | not possible | **`ke generate`, 7 artifact types** |
| Store what came back | not possible | **`--attach`** |
| Know what went stale | not possible | **`ke status --stale`** |
| Dependencies | resolved at runtime | **hash-pinned** |
| Tests | 465 | **600** |
| AI API calls, ever | 0 | **0** |

## What you can now do

```bash
ke search --tier 1 --learning-status not-started --limit 5
ke get MSF-2026-05-029

ke generate tutorial --id MSF-2026-05-029 | pbcopy    # → paste into any model
pbpaste | ke generate tutorial --id MSF-2026-05-029 --attach - --model <name>

ke status --stale        # what the source changed after you made it
```

`--text` folds case *and* punctuation, so `direct lake`, `Direct-Lake` and
`directlake` all find the same objects. Filters compose by AND; there is no query
language and no relevance ranking, because a wrong ranking hides things
convincingly, which is worse than no ranking at all.

Full worked examples in the README's new **Using your knowledge** section.

## The context pack

The output of `ke generate` carries everything a model needs and nothing it has
to be told twice: the instruction, the metadata it would otherwise guess at, the
stored article, related objects as one line each, the source link, and an explicit
note that the article is an original summary rather than the source's text.

Seven versioned templates under `ke/prompts/`. No templating language and no
placeholders — the template is instruction, the context is appended beneath it,
and concatenation cannot fail.

Every template forbids inventing specifics and says how to mark uncertainty,
because a confident fabrication is the most damaging thing any of them can
produce. Both properties are asserted by tests, as is the absence of
vendor-specific syntax — vendor independence erodes gradually and for good
reasons each time.

**The copy-paste step is not friction awaiting optimisation. It is the quality
control.** Everything generated here is plausible-sounding prose about a
technical subject, which is exactly where a wrong answer is hardest to spot and
most expensive to act on.

## Ownership, at its sharpest

`--attach` writes two things into the same directory, and they belong to
different people (ADR-0042):

| | Owner |
|---|---|
| `artifacts/tutorial.md` | **Yours.** Written once. Never touched again by anything automated. |
| the `generation:` block in `metadata.yaml` | **The engine's.** Bookkeeping *about* the artifact. |

That split is what makes staleness computable. The engine knows which revision an
artifact came from because it recorded it at the moment of attachment — not
because it inferred it later from prose it does not understand and must not
parse.

Replacing a **stale** artifact is the normal path. Replacing a **current** one
needs `--force`, because an artifact you have since edited by hand should not
vanish because you re-ran a command.

`--model` is recorded and never read. It exists so that when something reads
oddly in six months you can see what wrote it. Recording it is not a dependency;
reading it would be.

## Three defects found and fixed

### The prompt templates were not installed with the package

The one worth reading about.

Templates lived at `engine/prompts/`, one level above the package. Under `pip
install -e .` the path resolved and all seven loaded — which is how every test
and every manual check saw them. In a real, non-editable install they were never
copied at all. `ke generate` found **zero** templates and every artifact type
would have failed with "no prompt template".

**A command that was thoroughly tested and completely broken.**

Nothing in the existing suite could see it. Every other test runs against
`engine/` on `sys.path`, which is the right default and makes a whole class of
defect invisible: anything that works because a file happens to sit next to the
source.

`test_packaging.py` now builds and installs the package into a throwaway
virtualenv and checks what actually shipped. Slow by the standards of the rest of
the suite; that is the price of testing the thing that ships rather than the thing
in front of you.

The generalisable lesson, and the seventh variation on this project's recurring
one: **the test environment is itself an assumption, and assumptions in the test
environment are invisible by construction.**

### `stale_artifacts` was always true

It was a plain method sitting in a block of `@property` accessors. A bound method
is always truthy, so `if obj.stale_artifacts:` was silently true for every one of
the 222 stored objects, none of which have artifacts at all. `--stale` matched
all of them and looked entirely reasonable doing it.

Now a property. The regression test asserts truthiness rather than the value,
because `()` was never the failing case.

### `refresh_pack` wrote through a link path

`load_existing_objects` returns each object with a path relative to `indexes/` —
a Markdown link target, not a filesystem directory. M7 passed one to
`update_object` and got `TypeError: unsupported operand type(s) for /`.

The lucky version of the mistake. A string that happened to be a valid relative
path would have written objects somewhere else entirely, silently. Split into
`load_objects_with_dirs`, with each docstring naming the other.

## Security

Full review: [`M7_SECURITY_REVIEW.md`](../reviews/M7_SECURITY_REVIEW.md).

**M6's largest finding is closed.** `requirements.lock` pins every package in the
resolved graph with every sha256 PyPI publishes, and the weekly workflow installs
with `--require-hashes`. A tampered artifact fails the install rather than
executing in a job that holds a write token.

The lockfile is **generated, not written** — and for a good reason. The
hand-written first version pinned `sgmllib3k`, which feedparser used to depend on
and no longer does. pip rejected it outright, which was the good outcome; the bad
one would have been a file that installed cleanly while pinning the wrong graph.
`tools/lock_dependencies.py` discovers the closure with pip's own resolver.

Dependabot now watches pip and Actions (M6's S-4, closed).

**One finding stays open for a stated reason.** Pinning Actions to commit SHAs
(S-2) requires reading the `actions/*` repositories, which this session cannot
reach. Writing SHAs I could not verify would replace a weak guarantee with a
broken build and a false sense of a strong one — a workflow pinned to a hash that
does not exist fails at 06:00 on a Sunday for a reason that looks nothing like
its cause. The review contains the three commands to run for whoever has access.

**What M7 could have introduced and did not:** an AI API integration with a
credential, an endpoint, and an automated write path for untrusted model output.
It was designed out rather than secured.

## Operational readiness

New standing deliverable:
[`M7_OPERATIONAL_READINESS.md`](../reviews/M7_OPERATIONAL_READINESS.md).

Ten scenarios, each classified **graceful degradation**, **automatic recovery**
or **manual recovery**, and each backed by a test. All 30 test citations resolve.

**No scenario loses knowledge.** That follows from three earlier decisions:
objects are written before state, writes are both-or-neither, and nothing is ever
deleted.

**One manual-recovery path (O-1).** If the registry write fails after minting,
objects exist that the registry does not record. Nothing is lost, no Feature ID is
duplicated, and `ke validate` reports it. The scheduled workflow validates before
committing, so this state cannot reach the repository — it needs a human only
after a local `ke harvest`.

M7 fixed the *message*, which previously read `OSError: [Errno 28] No space left
on device` — accurate and useless. It now says how many objects are affected, that
nothing is lost, and what to run.

M7 deliberately did **not** fix the structure: reordering minting and persistence
is ADR-0031, and the reversed order has its own permanent failure mode. That
belongs to M8 with a `ke repair --registry` command (TD-10).

**The methodological finding is worth its own line.** Permission and disk-full
scenarios are conventionally tested with `chmod`. That does not work here: CI and
the development container run as **root**, and root bypasses permission bits
entirely. I wrote such a test and watched it pass against a directory that should
have refused the write. Failures are injected instead; one `chmod` test remains,
marked `skipif(root)`, so the distinction stays visible.

**Three times the behaviour was more careful than I expected** — a corrupt review
queue stops the run (losing `first_discovered_date` would permanently shift
Feature ID months), a failed write does not consume an ID, and the digest is
written even when the run had errors. Each was an earlier decision with a written
reason. That is the return on the ADRs.

## Known limitations

* **Generation is manual and has no batch mode.** Fifty objects is fifty round
  trips. `ke search --ids-only` makes the loop scriptable up to the paste.
* **Actions are still pinned by tag** (S-2), blocked as described above.
* **`load_existing_objects` is misnamed** — it returns a link, not a path.
  Renaming touches six call sites for a clarity gain smaller than the churn
  (TD-12).
* **The engine has still never recovered from a real failure.** Every scenario in
  the readiness review is induced; the weekly workflow has run zero times
  unattended. The tests are evidence about the code, not about the world.
* **The 35 objects with polluted revision history** from M3 remain, still
  surfaced as `REV002` warnings rather than rewritten.
* **No artifact has been generated from a real model yet.** The round trip is
  verified end to end with hand-written stand-in content; the quality of what a
  model returns for these prompts is unmeasured.
