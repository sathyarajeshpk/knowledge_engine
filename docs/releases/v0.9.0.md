## Executive summary

Every milestone since M0 was built on a sentence nobody had tested:

> A Domain Pack is pure data. The engine addresses packs by path and holds no
> knowledge of any specific pack.

Nine milestones of code, one pack in the repository. This release adds the
second one and finds out.

**It held.** The Azure pack adds 200 knowledge objects, 10 categories, 29
classification rules across 6 axes, an independent source and an independent ID
namespace — and `git show --stat --name-only 2a3c9e9 -- engine/` returns nothing
at all. Not one engine file.

Then having two of something exposed four defects that eight milestones with one
of it could not.

## What is new

### A second Domain Pack

```bash
ke harvest --pack azure
ke search --pack azure --tier 1
```

Azure was chosen over the originally-planned Power BI pack, and the reasoning is
recorded in ADR-0043. Power BI announcements arrive *inside* the Fabric release
feeds the first pack already harvests — a Power BI pack would have shared Fabric's
sources almost entirely, minted every announcement twice under two permanent
Feature IDs, and filled the cross-pack review queue with pairs that are not
mistakes. It would have tested the duplicate machinery thoroughly and pack
independence not at all.

Azure has genuinely separate sources, taxonomy, vocabulary and release cadence.
Power BI remains a first-class **category** inside the Fabric pack, findable with
`ke search --category power-bi`. ADR-0016 stands unamended.

### Cross-pack duplicate detection — reported, never resolved

When two packs hold what may be the same feature, the engine says so and does
nothing else. Both objects are minted, stored and indexed; neither is modified;
nothing is dropped, merged or blocked (ADR-0044).

```bash
ke review list --kind cross-pack
ke review resolve AZ-2026-07-038+MSF-2026-07-012
```

Two objects sharing a canonical URL across packs is often *correct* — one
announcement filed under two taxonomies, useful to two different questions — and
the engine cannot tell that from a true duplicate, so it does not try.

The property that makes this trustworthy is **order independence**: harvesting
Azure then Fabric produces a byte-identical report to Fabric then Azure. Detection
is not a pipeline stage; it reads what is on disk after all packs have harvested,
so it has no access to run order because it never sees one. **Feature IDs are
unaffected by pack order** — each pack mints from its own registry, for its own
items.

A resolution is stored once, at the repository root (`state/cross-pack.json`),
keyed on the canonical sorted pair — so acknowledging from either side clears it
for both, and it is not re-surfaced next week.

### Cross-pack references

`prerequisites: [AZ-2026-04-001]` in a Fabric object is now valid and validated.
References resolve against the whole repository, so a genuine cross-pack link
works and a typo is still caught (`REF001`, ERROR).

### The pack trust boundary, enumerated and enforced

ADR-0045 closes the set of things a pack can do. `ke validate` enforces it on
every pull request.

## Fixed

Four defects, all found by validating produced output rather than successful
execution, and all invisible with a single pack.

### A pack could read local files into stored knowledge — **critical**

`urlopen` speaks `file:`, `ftp:` and `data:` as happily as `http:`, and nothing
validated the scheme. A source declaring `url: file:///etc/hostname` fetched the
file, the pipeline stored its contents as a knowledge object, and the weekly
workflow committed and pushed it — verified against the real fetcher.

A local-file-read-to-exfiltration chain, reachable from a change that looks
entirely like configuration, in a process holding a repository write token.

Fixed with an `http`/`https` allowlist at three layers: when a source is built,
when a URL is fetched, and as `SEC002` (ERROR) in `ke validate`.

**The third layer exists because the first two were not enough, and the security
review said they were.** `Pack.source_definitions` is a lazy property, so the
allowlist fired only when something asked for the sources — and validation never
did. A hostile pack printed `ok: 1 pack(s), 0 knowledge object(s), no findings`
and would have failed at 03:00 on Sunday instead. Found by an installation-level
test running the real console script, after the in-process tests were green.

### A symlink in a pack could redirect every automated write — **high**

No symlink handling existed anywhere. Nothing in the CLI concatenates
attacker-controlled strings into a path, so there is no classic traversal — and
that reasoning is insufficient, because a path can be entirely engine-derived and
still land outside the pack when a *directory component* of it is a link.
`domain-packs/x/state -> ../../.git` is a legal git object that survives a clone.

Fixed with containment checks at pack discovery, at write time, and as `SEC001`
(ERROR) in `ke validate`. The boundary is `domain-packs/`, not the repository
root — `-> ../../.git` never leaves the repository and is precisely the case worth
stopping.

### One pack could take the whole harvest run down

`LockError` was the only exception the harvest loop caught, and it returned
immediately. A stuck lock on `microsoft-fabric` silently cost `azure` its entire
week. Anything else `harvest_pack` raised killed the run outright.

The loop now catches per pack, names which one failed and why, continues, and
restates the failures at the end. Exit code stays non-zero.

### `ke review --kind cross-pack` was rejected by its own CLI

M8 added `TaskKind.CROSS_PACK`, a provider for it and a row for it in the
rendered queue, and left behind a hard-coded choice tuple listing the three older
kinds. The choices now derive from the enum.

## Performance

Measured rather than estimated, with a committed benchmark
(`tools/measure_performance.py`). Full analysis in the M8 Performance Review.

| Operation | Cost |
|---|---|
| Harvest | 32 ms/object |
| Index rebuild | 11 ms/object |
| Search (full scan) | 2.9 ms/object |
| Memory | 4.8 KB/object |
| Repository growth | ~14 KB and 2 files per object |

A 10,000-object pack was measured and matched its projection to within 6%.

**The one finding worth acting on:** index rebuild is O(packs²) in full-pack
reads, because cross-pack detection runs inside each pack's index rebuild and
needs every pack. At two packs this is four reads and immeasurable; at ten it is
3.6× the single-pack cost for identical knowledge. A factor-of-two waste inside it
was fixed (the review report scanned every pack twice); the remaining `packs²` is
an architecture decision recommended for M9 rather than made here.

The first version of the benchmark was itself wrong — it timed everything with
`tracemalloc` running and inflated every number 4–5×. It completed cleanly, its
guards passed, and its numbers were internally consistent. Recorded as P-0.

## Upgrading

Nothing to do. Schema version is unchanged at 1, no Feature ID moved, no stored
object was rewritten, and no CLI flag changed meaning.

Two new validation errors can now fail a build that previously passed:

* **`SEC001`** — a symlink under `domain-packs/` pointing outside it.
* **`SEC002`** — a source URL that is not `http` or `https`.

Both shipped packs comply, asserted by a test.

`ke review --kind` now accepts `cross-pack` in addition to the three existing
kinds.

## Known limitations

* **Index rebuild is O(packs²).** Fine at two packs; address before the fifth.
* **Cross-pack detection lags one run.** Each pack indexes before the later packs
  have harvested, so a duplicate introduced this week is reported next week for
  every pack but the last. Hoisting the scan fixes this and the line above
  together.
* **Migration across independently-versioned packs is designed-for, not proven.**
  `schema_version` is per-pack, but no migration has run. M9 work.
* **Nothing validates that a pack's rules are *good*.** The Azure GA rule that
  classified previews as tier 1 was structurally valid YAML producing wrong
  knowledge. `docs/ADDING-A-PACK.md` warns about it; the engine cannot catch it.
* **35 `REV002` warnings** persist on Fabric objects — residue from the M3
  flip-flop bug, fixed in M3 and never rewritten because history is not rewritten.

> **⚠ Corrected 2026-08-08 — see [`docs/CORRECTIONS.md`](../CORRECTIONS.md) entry C-1.** The attribution to the M3 flip-flop bug above is **wrong**. All of these revisions date from 2026-08-01 and were produced by four harvest runs that each appended two revisions to the same object. The original wording is left in place deliberately; the correction record explains what was believed, what the evidence shows, and why the conclusion failed.
