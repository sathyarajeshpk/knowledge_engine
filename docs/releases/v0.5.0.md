# Release Notes — v0.5.0

**Milestone:** M4 — Orchestration and classification
**Date:** 2026-08-01
**Schema version:** 1 (unchanged)
**Status:** Knowledge is now organised, not just stored.

---

## Executive summary

M2 made the engine write knowledge. M3 made it safe to revisit. **M4 makes the
knowledge navigable** — every object now carries a tier, a priority, a category,
a difficulty, a workload and tags, decided by rules that live in `pack.yml` as
data rather than in engine code.

The milestone opened by paying down technical debt rather than adding features,
and that decision validated itself within the same milestone: the classification
stage slotted into the refactored pipeline as **one line**.

| | v0.4.0 (M3) | v0.5.0 (M4) |
|---|---|---|
| `harvest_pack` | 130 lines, 7 responsibilities | **89-line facade, 9 named stages** |
| Classified objects | 0 | **222** |
| Classification rules | 0 | **51, all in `pack.yml`** |
| Tests | 319 | **340** |
| Reclassification on re-run | — | **0** |

## The pipeline is now a list you can read

```python
STAGES = (discover, load_state, deduplicate, update_existing,
          gate_and_mint, classify_objects, persist_state,
          rebuild_indexes, append_run_log)
```

Adding a stage is one entry plus one function. Each stage carries its own
ordering constraint in its docstring — why updates precede minting, why state
persists after objects are on disk — instead of those reasons living in comments
far from the code they govern.

## Classification, in numbers

222 objects classified on the first pass and **zero on every pass after**:

| Axis | Distribution |
|---|---|
| **tier** | 37 act-now · 145 learn-soon · 40 awareness |
| **category** | real-time 53 · data-factory 40 · warehouse 35 · power-bi 23 · platform 19 · + 4 more |
| **difficulty** | intermediate 159 · advanced 51 · beginner 12 |
| **workload** | moderate 111 · light 93 · heavy 18 |
| **tags** | 209 objects tagged |
| **needs_review** | 45 — no rule could place them, so they are flagged rather than guessed |

Rules are data ([ADR-0034](../adr/0034-classification-writes-once.md)):

```yaml
tier:
  - name: generally-available
    any: [generally available, "(ga)", general availability]
    none: [preview]
    value: 1
```

First matching rule wins, in the order written. Every proposal records **which
rule produced it**, so disagreeing means editing a rule rather than reading
engine code.

**Write-once semantics** are what stop a rule tweak rewriting the archive:
classification lands when a field is unset, never when locked by `overrides`, and
never a second time. Changing your mind later is a deliberate act.

## Assumptions that were disproven

### 1. "Truthy means already set"

`applicable` tested falsiness to decide whether a field needed a value. `tier`
defaults to `AWARENESS` (3) and `difficulty` to `INTERMEDIATE` — **both truthy**
— so every enum-valued field looked already-decided and classification wrote
nothing.

**All 222 objects came back `tier: 3`.** That was the default, not a decision.

**Why it hid:** the pipeline reported "222 classified" because `reading_time`
had genuinely changed. The counts looked healthy and the distribution looked
like a real, if poor, classifier.

**Fix:** compare against the dataclass default. The honest question is *"has
anything ever set this?"*, not *"is this falsy?"*.

### 2. "Reading the object's own text is harmless"

`_haystack` included `category` and `tags` — fields classification itself
writes. A second harvest matched rules the first could not and reclassified four
more objects.

**Lesson:** a stage must not read its own output, or its result depends on
whether it has run before.

### 3. "A regression test I wrote covers the bug"

The first version of the feedback regression test **passed with and without the
fix**, because the fixture's rules did not actually create a feedback loop. It
had to be rewritten so a category value feeds a workload rule.

That is the second milestone running where a test claimed coverage it did not
have. **Verifying that a test fails against the old behaviour is the only thing
separating a guard from a decoration** — and it has now caught a worthless test
twice.

## Lessons carried forward

**Both M4 bugs reported success while being wrong.** Counts looked healthy,
distributions looked plausible. Running the pipeline is necessary but not
sufficient — you have to read what it produced.

**Paying down debt first paid off inside the same milestone.** Classification
landed as one line in a stage list rather than as surgery on a growing procedure.

## Known limitations

- **Substring matching is blunt.** `"sql"` matches `"nosql"`. Ordering and
  exclusions mitigate it; nothing warns about an over-matching rule (TD-13).
- **No retroactive reclassification.** Improving a rule leaves existing objects
  as they are. `ke reclassify` needs a dry-run and diff preview to be safe, so it
  is deferred rather than bolted on (TD-12).
- **The human-attention backlog is now 71 items** — 26 queued plus 45 flagged —
  with only one-at-a-time handling (TD-8, escalated to High).
- **A field deliberately set to its default value** is indistinguishable from an
  unset one, so classification may overwrite it. `overrides` is the remedy.
- Full list in [`M4_ARCHITECTURE_REVIEW.md`](../reviews/M4_ARCHITECTURE_REVIEW.md) §7.

## Breaking changes

None. `SCHEMA_VERSION` stays **1**. `HarvestReport` moved from `ke.harvest` to
`ke.report` and is still re-exported from its old home.
