# Release Notes — v0.3.0

**Milestone:** M2 — Identity, dedupe, storage and the first working pipeline
**Date:** 2026-08-01
**Schema version:** 1 (unchanged)
**Status:** **The engine now produces knowledge.**

---

## Executive summary

M0 built the container. M1 taught the engine to look. **M2 is the one where it
actually keeps something.**

Run `ke harvest` and it discovers from Microsoft's live sources, deduplicates
against what it already has, decides what is safe to make permanent, mints
Feature IDs, writes knowledge objects as Markdown, rebuilds the indexes and
appends the run log — in one pass, with no AI anywhere in it.

Against production it produced **222 knowledge objects** on the first run and
**nothing at all** on the second. That second number is the important one: it is
what makes a weekly unattended cron safe.

| | v0.2.0 (M1) | v0.3.0 (M2) |
|---|---|---|
| Knowledge objects written | 0 | **222** |
| CLI commands | `validate`, `discover` | + `harvest`, `review`, `index` |
| Tests | 249 | **287** |
| Files in the pack | 4 | **452** |
| Second run | — | **0 minted, byte-identical registry** |

## What you can now do

```bash
ke harvest --pack microsoft-fabric   # discover → store → index
ke review list                       # what was held back, and why
ke review approve <key>              # release one; mints on the next harvest
ke index                             # rebuild indexes from stored objects
ke validate --strict                 # verify the whole pack
```

A knowledge object is a directory that will outlive this engine:

```
knowledge/2026/07/MSF-2026-07-001-rayfin-ama-recap/
├── feature.md      # heading, short original summary, source link
└── metadata.yaml   # identity, provenance, dates, lifecycle, revisions
```

## Major decisions

### Ordering is the architecture ([ADR-0031](../adr/0031-harvest-ordering.md))

Three choices in `harvest_pack` carry the safety of the whole pipeline:

- **Dedupe before minting.** Minting is irreversible; deduplication is the last
  free check.
- **Registry saved after objects are on disk.** A crash then leaves an ID *gap* —
  recoverable — rather than a recorded ID pointing at nothing.
- **Run log appended always, even on a zero-item run.** GitHub disables a
  scheduled workflow after 60 days without commit activity, so a quiet week must
  still produce a commit.

### Three storage files, three failure policies ([ADR-0032](../adr/0032-state-failure-policies.md))

| File | Damaged → | Why |
|---|---|---|
| `seen.json` | **Degrade.** Start empty | Re-examining known items is cheap |
| `id-registry.json` | **Fail loudly** | Minting against a half-read registry reuses IDs, and a reused ID cannot be undone |
| `review-queue.json` | **Fail loudly** | It holds human decisions and original discovery dates — both unrecoverable |

Uniform error handling would have been simpler and wrong.

### An object is a pair of files, or it is nothing

`write_object` renders **both** documents before writing **either**. See below
for why this is stated so firmly.

## Assumptions that were disproven

### 1. "Writing two files in sequence is fine"

**Assumed:** write `feature.md`, then `metadata.yaml`.
**Reality:** a serialisation error between them left **222 orphaned `feature.md`
files** with no metadata, sitting at permanent-looking paths. On the very first
run.
**Fix:** render both, then write both, and clean up if the disk fails between.
**Lesson:** an entity spanning two files must be written as a unit.

### 2. "Computing the object path twice is harmless"

**Assumed:** the registry can build its own relative path.
**Reality:** it produced `knowledge/2026/08/…` while the validator expected
`2026/08/…`. All 222 objects failed validation.
**Fix:** use `KnowledgeObject.knowledge_subpath` — one source of truth.

### 3. "Testing the function tests the workflow"

**Assumed:** `ReviewQueue.approve()` works, therefore `ke review approve` works.
**Reality:** the report prints keys with the `sha256:` prefix stripped; the
lookup matched the full key. **The documented workflow was impossible.**
**Lesson:** follow the workflow you documented, not the function you wrote.

### 4. "PyYAML output is human-readable by default"

**Reality:** it emitted `&id001` / `*id001` anchors wherever a date object was
shared. `metadata.yaml` is read by humans in the GitHub UI; anchors are noise.
**Fix:** aliases disabled.

## Lessons carried forward

**Run it. All three bugs above were invisible to code review and obvious within
one minute of execution.** This release is the argument for building the product
before perfecting the design.

**Failure policy is a per-file decision.** "Handle errors consistently" would
have produced either a fragile engine or a dangerous one.

**Gaps are safe; reuse is not.** Wherever the pipeline can fail, it fails toward
skipping an ID rather than repeating one.

**Idempotency is a test, not an intention.** Second harvest: 0 minted, registry
byte-identical. Anything less and the weekly cron cannot be trusted unattended.

## Known limitations

- **No update path.** M2 only *creates*. If a source rewords an item we already
  store, nothing happens — silently. M5 owns revisions; until then the pack
  reflects first-seen state.
- **No classification.** Every object has empty `tier`, `category`, `difficulty`.
  M3 fills these.
- **No digest.** The run log carries counts, not content. M6 owns this.
- **26 items are queued** with only one-at-a-time approval. Bulk triage is debt
  (TD-8).
- **`harvest_pack` is doing too much** (TD-1) and `load_existing_objects` re-reads
  every object each run (TD-2). Both fine at 222 objects; neither will stay fine.
- Full list in [`docs/reviews/M2_ARCHITECTURE_REVIEW.md`](../reviews/M2_ARCHITECTURE_REVIEW.md) §6.

## Breaking changes

None for stored knowledge. `SCHEMA_VERSION` stays **1**.

`KnowledgeObject` gained `announcement_url` and `identity_confidence` — both
already documented in `SCHEMA.md` since v0.2.0, and added before any object
existed, so there is nothing to migrate. `TRACKING_PARAMS` moved from
`ke.acquisition.identity` to `ke.normalize`, where it belongs: core must not
import the acquisition subsystem, and the previous arrangement was a real import
cycle.

## What's coming in M3 — Classification

Tier, learning priority, category, difficulty and workload, proposed by rules
living in `pack.yml` rather than in code. The constraint M3 must respect:
**222 objects already exist**, so M3 is the first milestone that *updates* rather
than creates — and the field ownership model (ADR-0008) is about to earn its
keep for the first time.
