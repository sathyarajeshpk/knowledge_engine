# Release Notes — v0.1.0

**Milestone:** M0 — Foundation, Schema and Guardrails
**Date:** 2026-07-31
**Schema version:** 1
**Status:** First release

---

## Executive summary

Knowledge Engine is a system for building a personal library of technical
knowledge that you own outright — stored as ordinary text files, kept up to date
automatically, and usable with any AI assistant you like.

The problem it solves is familiar to anyone working in a fast-moving technology
area. Updates arrive faster than anyone can read them. What you do learn fades
within months. Your best explanations end up buried in a chat history you don't
control. And nothing anywhere keeps track of what you've actually learned versus
what you keep meaning to get to.

This release does not solve those problems yet. **It builds the foundations they
will rest on** — and does so deliberately, because these are the parts that are
almost impossible to change later.

An analogy: this release is the foundation, plumbing and wiring of a house. There
are no rooms yet. But the pipes are in the right places, the load-bearing walls
are where they need to be, and the electrical work has been inspected. Doing this
work first is unglamorous and it is the reason the rest can be built quickly and
safely.

**Three things were established that would have been very expensive to add
later:**

**The system can never overwrite your own work.** As you use the library you'll
record your own notes and progress — what you've learned, what you're partway
through, how topics connect. That information sits in the same files an automated
job rewrites every week. Without a hard rule, that job would eventually destroy
something you wrote, silently. So the rule is enforced by the software itself:
every field is owned either by the automation or by you, and the automation is
physically unable to write to yours. It fails with an error rather than
overwriting.

**The system does not depend on any AI company.** There is no AI involved in the
automated weekly process at all. When you want a tutorial or a set of interview
questions, the system prepares a self-contained document you paste into whatever
assistant you prefer — Claude, ChatGPT, Gemini, or something that doesn't exist
yet. Nothing is locked in, and there is no subscription. If every AI company
disappeared tomorrow, your library would be unaffected.

**It costs nothing to run.** No servers, no database, no paid services. The
target was ₹20 per month; the actual figure is zero. That is a design decision
rather than thrift — a system with no running cost never needs justifying and
never gets switched off during a quiet quarter.

**One honest caveat.** This release cannot yet fetch anything. The environment it
was built in blocked access to Microsoft's websites, so the list of sources is
deliberately empty. Guessing the addresses would have looked identical to having
verified them, and six months from now nobody could have told the difference.
Checking them is the first task of the next milestone.

## Major architectural decisions

Fifteen decisions are recorded in full, each with the alternatives that were
rejected and why, in [`docs/adr/`](../adr/). The ones that shape everything else:

### Files in Git, not a database ([ADR-0002](../adr/0002-github-as-the-storage-layer.md), [ADR-0003](../adr/0003-markdown-files-instead-of-a-database.md))

Knowledge is stored as Markdown and YAML in a private GitHub repository. No
database, no server, no third-party service.

*Why:* the knowledge must outlive the software that maintains it. Plain text in
Git will be readable in twenty years; it is diffable, hand-editable, and portable
by `git clone`. Git also provides complete version history for free, which is
what makes "never delete knowledge" enforceable rather than aspirational.

*Cost:* no ad-hoc querying, and no referential integrity from the storage layer —
which is a large part of why the validator exists.

### No AI in the scheduled pipeline ([ADR-0004](../adr/0004-no-ai-in-the-scheduled-pipeline.md))

Not "multiple providers behind an adapter" — **no AI call exists in the automated
pipeline at all.**

*Why:* an adapter is indirection, not independence; the provider still shapes the
output, the rate limits and the terms. Removing AI entirely makes vendor
independence structural, makes the cost genuinely zero, and makes the pipeline a
pure function — the same inputs always produce the same outputs, which is why the
whole test suite runs in half a second with no network access.

*Cost:* classification is rule-based and therefore less nuanced, and generation
requires a manual copy-paste step. Both were accepted deliberately.

*Enforcement:* a CI check fails the build if any scheduled workflow invokes the
generation command. It was added in this release, before the weekly workflow it
constrains exists.

### Field ownership ([ADR-0008](../adr/0008-field-ownership-model.md))

Every piece of metadata belongs to exactly one of three classes: owned by the
engine, proposed by the engine but overridable by you, or owned by you alone.

*Why:* this risk was **not** in the original design. It emerged from combining two
individually correct decisions — storing learning progress alongside the
knowledge, and having an automated job rewrite those files weekly. The
combination created a silent data-loss path that nobody asked about.

*Enforcement:* three mechanisms, not one. Assertions that run when the software
loads prove the classes never overlap. Every automated write passes through a
single gate that raises an error rather than overwriting. And the validator
checks that you have only locked fields that are lockable.

### Date-based, permanent Feature IDs ([ADR-0005](../adr/0005-date-based-feature-ids.md))

Every item gets an identifier like `MSF-2026-04-001` — pack, year, month,
sequence. Derived from the publication date where known, falling back to when it
was found.

*Why:* the identifier carries meaning without a lookup, sorts chronologically for
free, and can be created offline with no coordination. Counters are kept per
month, so adding older material later doesn't disturb anything already numbered.

*Permanence:* an ID is never changed and never reused, including for items later
replaced. This is why getting the format right before any data existed mattered.

### One directory per item ([ADR-0006](../adr/0006-directory-per-knowledge-object.md), amended by [ADR-0015](../adr/0015-create-object-subdirectories-on-demand.md))

Each item is a folder whose location never changes for its entire life.

*Why:* items eventually accumulate tutorials, images and code examples. The
alternative — a single file promoted to a folder when the first attachment
arrives — would move the item, breaking every link pointing at it.

### Corrections are revisions, never rewrites ([ADR-0009](../adr/0009-update-in-place-with-revisions.md))

When a source article changes, the existing item is updated in place and a
numbered revision is recorded. A new identifier is created only for a genuinely
new feature. Items that are superseded are marked, not removed. Generated
material whose source has moved on is flagged as out of date, never deleted.

### Three independent ways of ranking ([ADR-0010](../adr/0010-three-classification-axes.md))

Operational urgency, learning value, and source authority are separate fields
rather than one combined score.

*Why:* a pricing change is urgent but has nothing to teach; a community deep-dive
is not urgent at all but is the best possible basis for a tutorial. A single scale
cannot express either.

## What was implemented

11 commits · ~1,670 lines of engine code · ~1,195 lines of tests · **107 tests**
running in half a second · **one** runtime dependency · 15 decision records.

**The engine** (`engine/ke/`)

- The complete definition of a knowledge item: identity, source, classification,
  learning metadata, relationships, revision history and generated-content
  tracking.
- Permanent date-based identifiers with per-month numbering and validation.
- The field ownership registry and the write gate that enforces it.
- Domain Pack loading — packs are found by scanning a folder, so the engine
  contains no reference to Microsoft Fabric or any other subject anywhere.
- `ke validate` — **31 checks** covering pack structure, metadata correctness,
  identifier integrity, field ownership, file consistency, attachment integrity,
  a copyright word limit, and the identifier registry.
- A command-line interface with meaningful exit codes.

**The first Domain Pack** — `domain-packs/microsoft-fabric/`, configured and
ready, with its source list deliberately empty.

**Automation** — tests and validation run on every push, plus the guard that
prevents AI from entering the scheduled pipeline.

**Documentation** — the schema contract, vision, roadmap, development journal,
15 decision records, a file-by-file developer playbook with diagrams, a learning
guide for the underlying concepts, an architecture review, contribution
standards, and a changelog.

**Pre-merge review.** The codebase was reviewed cold before release, and the
claims it makes about itself were tested rather than trusted. Five defects were
found, reproduced, and fixed — including two that would have made a planned
future goal unreachable. The full record, with the original findings left as
written rather than tidied, is in
[`docs/reviews/M0_ARCHITECTURE_REVIEW.md`](../reviews/M0_ARCHITECTURE_REVIEW.md).

## What is intentionally not implemented

Everything below was possible to build in this release. Each was left out on
purpose.

| Not built | Why |
|---|---|
| **Any pipeline at all** — nothing fetches, stores or indexes | M0 builds only what is hard to retrofit once data exists. Building the pipeline first would have meant migrating data to fix the schema. |
| **Source addresses** | They could not be verified from the build environment. A guessed address is indistinguishable from a verified one. |
| **A web interface** | Impossible on a private repository on GitHub's free plan. Retrieval will be the folder structure plus a command-line tool. |
| **A database** | Files in Git are the source of truth ([ADR-0003](../adr/0003-markdown-files-instead-of-a-database.md)). |
| **Semantic search / embeddings** | Adds a service, a cost and a model dependency — the exact things this project avoids. Plain search first; revisit only on demonstrated failure. |
| **Relationship validation** | Nothing populates relationships yet. Validating an always-empty field proves nothing. Arrives in M4. |
| **Automatic content generation** | Tutorials and posts are produced when you ask. The system will never fill your library with material you didn't request. |
| **A linter or code formatter** | A tooling choice worth making deliberately rather than assuming. |

## Known limitations

**No source has been verified. This blocks the next milestone.** The build
environment blocked access to `*.microsoft.com`, so the source list is empty with
candidates recorded as comments. Checking each one is M1's first task and nothing
else in M1 can start before it.

**Relationships are not validated.** An item can currently reference a
prerequisite that doesn't exist and pass validation. Referential integrity and
cycle detection arrive in M4.

**Validation runs in permissive mode.** Warnings are reported but do not fail the
build. This tightens once the first pack contains real content. A fresh clone now
passes in strict mode, which one of the pre-merge fixes made possible.

**Hand-editing is stricter than it should be.** Every metadata field is required,
even when empty, so deleting a blank line from a file produces an error. This
conflicts with the design's own emphasis on hand-editing your learning notes, and
is recorded in the architecture review as worth relaxing.

**Deliberately deferred, and recorded rather than forgotten:** enforcing the
code/data separation rule automatically, pinning GitHub Action versions to exact
revisions, a pull request template, and declaring the version number in one place
instead of two. None threatens the next two milestones.

**The unresolved decision that matters most.** Microsoft's Fabric and Power BI
publications overlap heavily. Whether Power BI material appearing in the Fabric
feed belongs to the Fabric pack or the Power BI pack **must be decided before any
identifier is created** — because identifiers are permanent, and getting it wrong
produces duplicates that can never be cleaned up. This is a decision, not code,
and it is the highest-severity open item in the project.

## Breaking changes

**None.** This is the first release.

Two notes for the future:

- **Schema version 1 is the baseline.** Every stored item records the version of
  the file layout it was written against. Removing or renaming a field will
  require a version increase and a migration; adding an optional field will not.
- **Before version 1.0, the command-line interface may change.** The stability
  guarantee that actually matters at this stage is the schema version, because it
  protects your data rather than your commands.

## What's coming in M1 — Discovery

M1 makes the system fetch. It reads from real sources, normalises what it finds,
and prints it. **It writes nothing** — storage arrives in M2, so that discovery
can be verified before anything permanent is created.

- Verify and record every source address. *Blocking; first task.*
- Adapters for feeds, sitemaps, and documentation repositories.
- Normalisation: cleaning addresses, extracting text, and parsing publication
  dates while recording how confident that parse is.
- `ke discover --dry-run`, printing what was found without storing it.
- Per-source failure isolation, so one broken feed never stops a run.

**Decision required before M1 begins:** the Fabric / Power BI boundary described
above.

The full plan through M9 is in [`docs/ROADMAP.md`](../ROADMAP.md).

## Why M0 is an important milestone

It is reasonable to ask what was achieved by a release that cannot yet do
anything. Four things, each of which becomes far more expensive later.

**The schema exists before the data does.** Once thousands of items are stored,
changing their shape means writing migrations and risking corruption. Getting it
right while the cost of change is zero is the single highest-leverage thing this
release did.

**Identifiers are permanent, so their format had to be settled first.** A
formatting mistake in an identifier scheme is not a bug you fix — it is a bug you
live with, because the identifiers are already written into files, links and
notes. Choosing the format before minting a single one is the only chance
available.

**The rules became mechanisms.** This is the property that matters most, and it
generalises well beyond this project. A rule written in a document is a rule that
will eventually be broken; a rule enforced by software that fails loudly is a
rule that holds. Every important rule here is now a mechanism:

| Rule | What enforces it |
|---|---|
| Knowledge is never deleted | The vocabulary has no way to express deletion |
| The engine never writes your fields | An error is raised instead |
| Ownership classes never overlap | The software refuses to load |
| Identifiers are unique and permanent | The validator fails the build |
| No AI in the scheduled pipeline | Automation scans the workflows |
| No copying third-party article text | The validator fails the build |

**Reviewing before merging paid for itself.** Five defects were found by testing
the code's claims rather than trusting them — including two that would have
permanently blocked a planned goal. Every one was invisible in the state this
release ships in: one pack, no items, nothing committed. Finding them now cost an
hour. Finding them in M2, M5 or M8 would have cost a debugging session inside a
milestone with real data at stake.

That last point produced the most useful lesson of the milestone, and it is worth
carrying forward: **a test suite tests the world as it is today, not as later
milestones will make it.** Two of the five defects only appeared once a second
pack existed; one only appeared after an actual commit-and-clone cycle. The
multi-pack fixture is now permanent rather than something scheduled for M8.

M0 built no features. It built the conditions under which every later feature can
be built quickly, safely, and without fear of quietly losing something that
matters.
